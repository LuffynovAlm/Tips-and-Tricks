BMad build cycle — help → sprint plan → build → review6.12.412

Start with /bmad-help to set the context
It reads your artifacts and sprint status, says where you are and which workflow is next. Ask it a real question: /bmad-help what is the next story of epic 2 and what context does it need?
Install uv first
Every 6.12.4 workflow skill starts with a uv run render step and HALTS if uv is missing. npx bmad-method install needs it too
Set up the repo's agent instructions once
/bmad-project-context (setup / adopt / refresh / record / audit) maintains a verified block in AGENTS.md. It replaces generate-project-context; use record when an agent repeats a mistake so it becomes a pitfall
/bmad-sprint-planning before the first build
It runs a readiness gate (PASS / CONCERNS / FAIL) on PRD, UX, architecture and epics, then writes sprint-status.yaml. Run it again with intent status any time: /bmad-sprint-planning show sprint status
/bmad-build in a fresh context
/clear, then /bmad-build with a story, an issue link, a spec file or just the intent. One flow: clarify → plan → implement → review → present. The spec file is the hand-off, not the chat
Build resumes where it stopped
Rerun /bmad-build: it lists active specs (draft, ready-for-dev, in-progress, in-review) and lets you resume one instead of starting over
Keep one spec = one user goal
Build aims at a single shippable goal in roughly 900–1600 tokens. Several independent deliverables → split them, or use /bmad-spec to break a spec into stories
Add an independent review when it matters
Build already reviews. For a second look in a new session, ideally another model: /bmad-code-review, or /bmad-review lenses=edge-case-hunter,verification-gap on a diff or a document
Walk through the change as a human
/bmad-walkthrough explains what the change is for, what to inspect closely and how to test it before you merge
Many stories in a row
/bmad-story-automator chains create → dev → QA → review → retro across an epic; bmad-loop runs unattended and pauses on escalations for /bmad-loop-resolve <story-key>
Old skill names still work
bmad-quick-dev, bmad-create-prd, bmad-sprint-status, bmad-checkpoint-preview, bmad-market-research… forward to the new skills (shims, removed with v7 only). Prefer the new names
Log the AI cost in the deliverable
/cost before closing, then the AI usage: line in the spec's *Implementation Notes* (bmad-build) or the story's *Dev Agent Record* (v6), one line per session, a total at the end

BMad loop — unattended build with bmad-loop6.12.410

Install once, then init the project
/bmad-loop-setup installs the tool from Git (uv tool install "bmad-loop[tui] @ git+https://github.com/bmad-code-org/bmad-loop.git"), then bmad-loop init --project "<project root>" --cli claude registers the hooks and writes .bmad-loop/policy.toml
Check before the first run
bmad-loop validate --project "<project root>" preflights the install and the per-role adapter config. Fix what it reports before you start a run
Accept the first-run dialogs by hand
Start claude once in the project and accept the workspace-trust and hooks-approval prompts. Spawned sessions cannot answer them, and the run stalls there
One CLI or several
init --cli claude --cli codex sets up more than one profile. Valid names: claude, codex, gemini, copilot, antigravity
Watch it live
bmad-loop tui opens the Textual dashboard (installed with the [tui] extra) to follow the run, the story and the sessions
Escalation = a question for you
A run pauses on a CRITICAL escalation: a contradiction or gap in the frozen spec that a session could not resolve safely. Resolve it in an interactive session with /bmad-loop-resolve <story-key>. The human makes the call; the spec is then updated and the story re-driven
Environment fault
If the run paused on an environment problem rather than a spec problem, fix the environment, then bmad-loop resume <run>. Do not edit the spec for it
Triage the deferred work
bmad-loop sweep verifies each open entry in the deferred-work ledger against the code and sorts it into bundles, already resolved, blocked, skip or human decision. It is read-only
Keep the stories small
An unattended session cannot ask questions. Give the loop stories with clear acceptance criteria and one goal each; a vague story is the most common reason for an escalation
Track the cost per session
Every loop session is its own Claude session. Use /cost on the sessions you care about and log one AI usage: line per session in the spec, as with /bmad-build

BMad story cycle — help → create → dev → reviewv6 legacy8

Start with /bmad-help to set the context
It reads your artifacts and sprint status, says where you are and which story / workflow is next. Ask it a real question: /bmad-help what is the next story of epic 2 and what context does it need?
Generate project-context.md once
/bmad-generate-project-context writes the project's AI rules. Story creation and dev load it, so every story inherits the same conventions without you repeating them
/bmad-create-story in a fresh context
/clear, then /bmad-create-story 2.3. The story file gets everything the dev needs (ACs, tasks, architecture notes, files to touch) — it is the hand-off, not the chat
Validate the story before coding
Run the create-story validate action ([VS]) to catch missing context while it is still cheap to fix
/bmad-dev-story <story file> in another fresh context
/clear between create and dev. Dev works task by task and checks them off in the file, so rerunning on the same story resumes at the first unchecked task
Review in a new session, ideally another model
/bmad-code-review with fresh eyes. Issues → back to /bmad-dev-story, approved → next /bmad-create-story
Many stories in a row
/bmad-story-automator chains create → dev → QA → review → retro across an epic
Log the AI cost in the story
/cost before closing, then the AI usage: line in the *Dev Agent Record* (one line per session, a total at the end)

HVE RPI — rpi-review and friends11

One RPI phase per session
Research, plan, implement, review each write a file in .copilot-tracking/. /clear between phases: the next phase reads the file, not the chat, so you pay for less context
Always close with /rpi-review
It compares plan vs changes and writes RV-xxx findings with a route: defect → /rpi-implement, missing decision → /rpi-plan, missing evidence → /rpi-research, extra work → follow-up
Give /rpi-review explicit paths
/rpi-review plan=<plan.md> changes=<changes.md> — it stops if several unrelated tasks match
depth=deep only on purpose
Standard is the default and fast. Deep is never inferred from size or risk: ask /rpi-review depth=deep for critical changes only
Review is resumable
An interrupted review (started) continues from its record. A finished review is reused unless you ask for a new one (-review-2.md)
Answer findings one by one
In manual mode it asks per finding: *use suggested action*, *gather more info*, *skip*, *finish*. Skipped material findings block a conformant outcome — on purpose
Critique the plan before coding
/rpi-plan runs a standard critique by default; /rpi-plan-critique plan=<file> for an independent second look. Fixing a plan is cheaper than fixing code
Challenge a decision
/rpi-challenger subject=... asks one skeptical question per turn, no answers given — good before an architecture choice
Understand a change
/rpi-walkthrough target=<files> detail=brief explains segment by segment with file links
Copilot equivalent
/task-research, /task-plan, /task-implement phaseStop=true, /task-review scope=today, or /rpi task=... for the autonomous RPI Agent
BMad or RPI?
BMad spec / story → /bmad-code-review. RPI-tracked task (plan + changes in .copilot-tracking/) → /rpi-review. Each review expects its own artifacts

Join an existing session — Claude Code6

claude -c
Continue the most recent conversation of the current folder, with its full history
claude -r
No argument: pick a past session from a list. claude -r <id or name> jumps straight to one
/resume
Same picker from inside a running session
claude -r <id> --fork-session
Resume into a new session ID: you branch off without changing the original conversation
Resume in the right folder
Sessions are stored per project directory: cd into the project first, or -c finds nothing
Resume the work, not the chat
For BMad / RPI, a fresh /clear session + the artifact (spec / story file, plan, /rpi continue) is often cheaper than resuming a long conversation

Join an existing session — GitHub Copilot6

Chat history in VS Code
History (clock) icon in the Chat view → reopen a previous chat session and keep going
Copilot CLI
copilot --continue reopens the last session, copilot --resume lets you pick one, /resume from inside the CLI
/checkpoint (HVE)
/checkpoint mode=save description=story-2-3 before leaving, then /checkpoint mode=continue description=story-2-3 in a new chat to restore the context
/rpi continue=1 (HVE)
The RPI Agent picks up suggested work item 1 from its last Discover phase
Compact handoff button (HVE agents)
Compacts but keeps every .copilot-tracking path and the current phase — use it instead of a plain /compact
BMad in Copilot
State lives in sprint-status.yaml and the spec / story file: in a new chat, /bmad-help or /bmad-sprint-planning show sprint status tells you where you left off
